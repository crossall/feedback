# Feedforward 시스템 실행 로드맵

이 로드맵은 현재 기능을 중단하지 않으면서 개인정보 약속과 실제 데이터 흐름을 먼저 맞추고, 그 다음 인증과 보유기간을 강화한 뒤, 반복된 프로젝트 코드를 공통 기반으로 통합하는 순서입니다. 기능 확대보다 신뢰 경계의 수정이 앞섭니다.

## 1 우선순위 원칙

1. 외부 전송과 개인정보의 불일치를 먼저 해결합니다.
2. 다른 사용자의 데이터에 접근할 수 있는 권한 문제를 다음으로 해결합니다.
3. 보유기간과 삭제를 자동으로 집행합니다.
4. 공통 모듈과 테스트로 같은 문제가 다시 생기지 않게 합니다.
5. 관찰 지표와 수업 효과 지표를 연결합니다.

## 2 P0 외부 전송 일치

### 목표

개인정보 처리방침, AI 요청 코드, 실제 네트워크 경로가 같은 내용을 설명하도록 만듭니다.

### 작업

- 일반 PDF와 Google Docs 평가 프롬프트에서 이름, 학년, 반, 모둠을 제거합니다.
- 제출자를 구분해야 하는 내부 결과에는 서버 내부의 요청 ID 또는 교사가 정한 가명을 사용합니다.
- `buildEvaluationPrompt` 같은 단일 함수에서 외부 AI 전송 본문을 만들고 식별정보가 포함되지 않았는지 검사합니다.
- 테스트용 이름, 학급, 이메일, 전화번호를 넣어 OpenAI와 Anthropic 요청 본문에 남지 않는지 회귀 테스트합니다.
- Vercel AI Gateway를 실제로 사용할지, 제공자 API를 직접 사용할지 결정합니다.
- 선택한 경로에 맞춰 개인정보 처리방침의 수탁자, 국외 이전, 보관 설명을 수정합니다.
- 요청 본문을 저장하지 않는 전송 감사 이벤트를 정의합니다.

### 완료 조건

- 자동 테스트가 직접 식별정보 외부 전송을 차단합니다.
- 구조 문서와 개인정보 처리방침이 실제 요청 URL과 전송 필드를 정확히 설명합니다.
- 교사 화면에서 AI에 전송되는 정보 범위를 사전에 확인할 수 있습니다.

## 3 P1 교사 인증과 소유권

### 목표

숫자 교사 ID를 로그인 수단으로 쓰지 않고 모든 교사 데이터 요청에서 서버 세션과 소유권을 확인합니다.

### 작업

- 학교 계정 또는 승인된 교사 계정 기반 로그인 방식을 선택합니다.
- HttpOnly, Secure, SameSite 쿠키를 사용하는 서버 세션을 발급합니다.
- `/api/teachers/[teacherId]/*`에서 세션의 교사 ID와 경로의 교사 ID가 같은지 검사합니다.
- 평가, 응답, API 키, OAuth 토큰의 소유권 검사를 공통 함수로 만듭니다.
- 프로젝트 4의 코드 기본 비밀번호를 제거하고 배포 환경변수 누락 시 시작 또는 배포를 실패시킵니다.
- 프로젝트별 워크스페이스의 공유 저장 API에 역할 토큰과 네임스페이스 권한을 적용합니다.
- 권한 거부 이벤트는 본문 없이 리소스 종류, 요청자, 시간, 결과를 기록합니다.

### 완료 조건

- 교사 A의 세션으로 교사 B의 평가 목록, API 키 상태, 응답에 접근할 수 없습니다.
- 인증이 없는 모든 변경 요청은 401, 소유권이 없는 요청은 403을 일관되게 반환합니다.
- 운영 환경에 기본 비밀번호가 존재하지 않습니다.

## 4 P1 보유기간과 삭제

### 목표

정책에 적힌 보유기간이 데이터 객체와 자동 작업에서 실제로 집행되도록 합니다.

### 작업

- 평가 설정, 응답, 산출물, 피드백, OAuth 토큰, 로그에 데이터 분류와 `expiresAt`을 추가합니다.
- 프로젝트 종료 시각과 마지막 활동 시각을 분리합니다.
- 보유기간 계산을 한 모듈에서 수행하고 프로젝트별 임의 계산을 금지합니다.
- 매일 만료 객체를 찾는 삭제 작업을 실행합니다.
- 삭제는 관련 객체 전체를 찾은 뒤 명시된 경로만 제거하고, 성공과 실패를 감사 기록에 남깁니다.
- 교사 화면에 프로젝트 삭제와 학생별 삭제를 제공하고 삭제 범위를 미리 보여 줍니다.
- 삭제 후 조회 불가와 Blob 부재를 확인하는 검증 작업을 추가합니다.
- 백업과 임시 파일의 보유기간도 운영 문서에 포함합니다.

### 완료 조건

- 만료된 테스트 프로젝트가 예약 작업 뒤 조회되지 않습니다.
- 삭제 감사 기록에는 본문이 없고 대상 종류, 개수, 요청 주체, 시간, 결과만 남습니다.
- 교사와 학생의 권리 요청을 처리할 수 있는 운영 절차가 있습니다.

## 5 P2 공통 플랫폼 모듈

### 목표

프로젝트별 수업 경험은 유지하면서 저장, 인증, AI 호출, 입력 검증, 감사, 삭제를 공통화합니다.

### 제안 모듈

```text
lib/server/auth
  requireTeacherSession
  requireResourceOwner
  issueParticipantToken

lib/server/repository
  JsonRepository
  VercelBlobRepository
  conditionalWrite
  listByNamespace

lib/server/ai
  EvaluationProvider
  OpenAIProvider
  AnthropicProvider
  redactDirectIdentifiers
  validateStructuredOutput

lib/server/governance
  classifyData
  calculateExpiry
  recordAuditEvent
  deleteExpiredData
```

### 마이그레이션 순서

1. 새 공통 인터페이스를 기존 코드 옆에 추가합니다.
2. 가장 단순한 Project Expo 저장 API를 공통 저장소로 옮깁니다.
3. Project 1, Meta1, Confesta를 차례로 옮기고 이전 경로 읽기를 유지합니다.
4. 일반 평가와 세션의 AI 호출을 공통 제공자 인터페이스로 옮깁니다.
5. 프로젝트 4는 동시 읽기, 재시도, 다단계 기록 요구를 보존한 상태에서 마지막에 옮깁니다.
6. 모든 호출이 전환되고 데이터 마이그레이션 검증이 끝난 뒤 중복 코드를 제거합니다.

### 완료 조건

- 프로젝트별 Route Handler에는 프로젝트 고유 입력과 도메인 호출만 남습니다.
- 인증, 식별정보 제거, 외부 AI 오류, Blob 충돌이 모든 프로젝트에서 같은 방식으로 처리됩니다.
- 이전 데이터 경로를 읽는 계약 테스트가 통과합니다.

## 6 P2 자동 테스트 체계

### 단위 테스트

- AES 토큰 암복호화, HMAC 서명, 만료와 역할 거부
- 평가 설정, 동료 질문, 자기평가, 세션, 프로젝트 4 설정 정규화
- 루브릭 배점 합계와 구조화 결과 검증
- 학생 식별정보 제거와 허용 필드 목록
- 보유기간 계산과 삭제 대상 선택

### 계약 테스트

- OpenAI와 Anthropic 응답을 같은 `Evaluation` 구조로 변환
- Vercel Blob 읽기, 조건부 쓰기, 충돌, 재시도
- Google Docs 주소 파싱, 공개 문서 읽기, OAuth 쓰기
- 개인정보 처리방침에 공개된 제공자와 코드의 실제 호스트 일치

### E2E 테스트

- 교사 로그인, 평가 저장, 다시 불러오기, 직접 PDF 평가
- Google OAuth 상태와 Docs 결과 추가 실패 안내
- 세션 생성, 학생 단계 진행, 교사 결과 확인
- 프로젝트 4 학생과 후배 역할, 단계 잠금, AI 판단, 최종 제출
- 공개 방명록 작성, 관리자 공개와 답변, 동시 수정 충돌
- 다른 교사의 데이터 접근 거부

### 완료 조건

`npm run pipeline`에 테스트 명령이 포함되고, pull request에서 핵심 권한과 개인정보 회귀가 배포 전에 차단됩니다.

## 7 P3 관찰성과 수업 효과

### 운영 관찰

- Route Handler별 요청 수, 지연시간, 오류 분류
- AI 제공자와 모델별 성공률, 구조 검증 실패율, 비용과 응답시간
- Blob 읽기와 쓰기 지연, 충돌, 재시도, 삭제 성공률
- 토큰 만료와 권한 거부 비율

### 교육 관찰

- 학생이 AI 제안을 수용 또는 거절한 비율과 이유 작성률
- 초안과 최종본 사이에 실제 수정이 발생한 비율
- 동료, 발표, 후배 평가에서 반복되는 이해 어려움
- 다음 수업에서 교사가 루브릭이나 안내를 수정한 기록

운영 지표와 교육 지표를 같은 대시보드의 한 점수로 합치지 않습니다. 운영 지표는 시스템 건강을, 교육 지표는 학습 설계의 근거를 보여 줍니다.

## 8 변경 단위

각 pull request는 다음 항목을 포함합니다.

- 변경한 사용자 흐름과 역할
- 새로 입력, 저장, 전송, 삭제되는 데이터
- 인증과 권한 경계
- 실패와 재시도 방식
- 시스템 지도와 관련 문서 변경
- 단위, 계약, E2E 검증 결과
- 개인정보 처리방침 변경 필요 여부

외부 AI 전송 필드, 저장 경로, 권한, 보유기간을 바꾸는 pull request는 코드와 문서를 분리해 배포하지 않습니다.

## 9 90일 제안 순서

| 기간 | 핵심 결과 | 배포 조건 |
| --- | --- | --- |
| 1주에서 2주 | 학생 식별정보 제거, AI 경로 결정, 정책 정합성 | 외부 전송 회귀 테스트 통과 |
| 3주에서 5주 | 교사 인증, 소유권 검사, 기본 비밀번호 제거 | 교차 계정 접근 테스트 통과 |
| 6주에서 8주 | 만료 시각, 자동 파기, 삭제 확인 | 만료 프로젝트 삭제 검증 통과 |
| 9주에서 10주 | 공통 저장과 AI 어댑터 1차 전환 | 이전 경로 계약 테스트 통과 |
| 11주에서 12주 | 핵심 E2E와 운영 지표 | `npm run pipeline`과 배포 후 합성 점검 통과 |

일정은 기능 수가 아니라 위험을 닫는 순서로 조정합니다. P0와 P1이 끝나기 전에는 학생 데이터 범위를 넓히는 새 기능을 추가하지 않습니다.
