# Feedforward 시스템 철학

Feedforward는 평가를 학생을 분류하는 마지막 절차가 아니라 학생이 다음 행동을 선택하도록 돕는 학습 과정으로 봅니다. 교사는 기준과 맥락을 설계하고, AI는 기준에 따른 분석과 제안을 제공하며, 학생은 그 제안을 판단하고 수정과 성찰의 주체가 됩니다. 시스템의 성공은 더 많은 점수를 자동으로 만드는 데 있지 않고, 근거 있는 피드백이 실제 수정과 다음 수업으로 이어지는 데 있습니다.

## 1 평가의 끝은 다음 행동이다

점수는 현재 위치를 요약하지만 무엇을 해야 하는지 충분히 설명하지 못합니다. 모든 평가 결과는 학생이 바로 실행할 수 있는 다음 행동과 연결되어야 합니다.

현재 일반 AI 평가 스키마가 `nextStep`을 필수로 요구하고, 프로젝트 4가 동료 의견, AI 판단, 최종 대본, 자기평가를 순서대로 배치한 이유가 여기에 있습니다. 보고서도 총점보다 강점, 개선점, 다음 행동을 함께 제시해야 합니다.

결정 기준은 단순합니다. 새로운 결과 화면이나 지표가 학생과 교사의 다음 행동을 바꾸지 못한다면 우선순위를 낮춥니다.

## 2 기준은 모델보다 먼저 온다

AI 모델의 유창함은 평가의 타당성을 보장하지 않습니다. 과제의 목적, 성공 기준, 배점, 학생에게 기대하는 증거를 교사가 먼저 정해야 합니다. 모델은 그 기준을 적용하는 도구입니다.

따라서 Feedforward는 모델 선택보다 과제 설명과 루브릭 입력을 앞에 둡니다. 구조화된 출력도 루브릭 항목명과 최대 점수를 유지하도록 설계합니다. 모델을 바꿔도 평가의 핵심 기준은 유지되어야 하며, 같은 제출물에 대한 결과 차이를 설명할 수 있어야 합니다.

새 AI 기능을 추가할 때에는 “어떤 모델을 쓸까”보다 먼저 “교사가 어떤 기준을 제공하고 학생이 어떤 근거를 보게 될까”를 묻습니다.

## 3 AI는 제안자이며 최종 판정자가 아니다

AI는 많은 내용을 빠르게 읽고 기준별 초안을 만들 수 있지만, 수업 맥락, 학생의 과정, 의도, 정서, 공정성에 대한 최종 책임을 질 수 없습니다. 최종 교육적 판단은 교사가 수행합니다.

프로젝트 4의 AI 피드백 단계는 이 원칙을 제품 동작으로 구현합니다. 학생은 AI의 각 제안을 그대로 받지 않고 수용 또는 거절을 선택하고 이유를 남깁니다. 거절은 오류가 아니라 판단의 증거입니다. 좋은 시스템은 높은 AI 수용률을 목표로 하지 않고, 제안과 근거를 비교할 수 있게 해야 합니다.

AI 결과를 자동으로 생활기록, 성적, 선발, 징계에 확정 반영하는 기능은 이 철학과 맞지 않습니다. 그런 결정에는 교사의 검토와 명시적 승인, 이의제기 절차가 필요합니다.

## 4 학생은 피드백의 대상이 아니라 판단의 주체다

학생에게 피드백을 보여 주는 것만으로 학생 주도성이 생기지 않습니다. 학생이 의견을 비교하고, 받아들일 것과 거절할 것을 정하고, 최종본을 수정하고, 자신의 선택을 설명할 수 있어야 합니다.

Feedforward는 동료평가, 대표 작품 선정 이유, AI 제안 판단, 최종 제출, 성찰을 기록합니다. 이 기록은 학생을 감시하기 위한 로그가 아니라 학습 과정의 증거입니다. 화면은 학생에게 왜 이 질문을 하는지, 누가 결과를 보는지, 어떤 단계에서 수정할 수 있는지 알려야 합니다.

학생에게 선택권이 없는 활동이라면 선택하는 것처럼 꾸미지 않습니다. 필수 단계와 선택 단계를 명확히 표시하고, AI 사용을 원하지 않는 경우 교사 피드백 같은 대체 경로를 제공합니다.

## 5 한 번의 평가보다 여러 관점의 교차가 중요하다

산출물의 품질은 교사, 동료, 실제 청중, 학생 자신이 서로 다른 부분을 봅니다. 하나의 점수나 한 번의 AI 응답으로 이 관점을 합치면 중요한 차이가 사라집니다.

프로젝트 4는 모둠 동료평가, 다른 모둠 발표평가, AI 피드백, 후배 평가, 자기평가를 구분합니다. 통합 세션도 PDF 또는 Docs AI 평가, 동료평가, 자기평가, 성찰을 독립 단계로 유지합니다. 각 관점의 출처를 보존한 뒤 교사와 학생이 함께 해석해야 합니다.

따라서 대시보드는 서로 다른 척도를 억지로 하나의 평균으로 만들지 않습니다. 정량 자료는 비교 가능한 범위에서 집계하고, 정성 자료는 주제와 구체적 근거를 함께 보여 줍니다.

## 6 설명 가능성은 정확성의 일부다

학생과 교사는 점수만이 아니라 어떤 기준과 어떤 근거로 그 결과가 나왔는지 알아야 합니다. 근거를 찾을 수 없는 피드백은 문장이 자연스러워도 사용할 수 없습니다.

일반 평가 결과는 기준별 점수와 피드백을 분리하고 강점과 개선점을 제출물의 구체적 요소에 연결하도록 요구합니다. 후배 평가와 발표평가는 질문별 반응을 남깁니다. 시스템 변경도 API 인벤토리, 시스템 지도, 구조 문서를 코드와 함께 갱신해 운영자가 데이터 흐름을 설명할 수 있어야 합니다.

새 지표를 추가할 때에는 계산식, 입력 자료, 누락 자료 처리, 결과를 볼 수 있는 역할을 문서화합니다. 설명할 수 없는 종합 점수는 만들지 않습니다.

## 7 개인정보 보호는 동의문이 아니라 데이터 흐름이다

개인정보 최소화는 안내문 한 줄로 달성되지 않습니다. 입력 필드, 토큰, 저장 경로, AI 전송 본문, 로그, 보고서, 삭제 작업에서 같은 원칙이 실행되어야 합니다.

Feedforward가 지향하는 원칙은 학생 계정을 만들지 않고, 개인 이메일과 전화번호를 요구하지 않으며, 수업에 필요한 별칭과 최소 정보만 처리하는 것입니다. API 키와 OAuth 토큰은 암호화하고 서버 밖으로 보내지 않습니다. 학생 정보는 광고, 상업적 프로파일링, 자체 모델 학습에 사용하지 않습니다.

현재 일반 AI 평가가 학생 이름과 학급 정보를 프롬프트에 포함하는 동작은 이 원칙과 맞지 않습니다. 시스템 철학은 현재 구현을 미화하기 위한 문장이 아니므로 이 차이를 명시하고 우선 수정합니다. 개인정보 관련 약속은 코드로 자동 검사할 수 있어야 합니다.

## 8 교사는 기술 설정자가 아니라 교육 설계자다

교사의 시간은 API 오류와 파일 형식을 해결하는 데 쓰기보다 평가 목적, 기준, 학생 지원을 설계하는 데 쓰여야 합니다. 기술은 교사의 판단을 가리는 자동화가 아니라 반복 업무를 줄이는 기반이어야 합니다.

평가 보관함은 한 번 만든 과제와 루브릭을 다시 쓰게 하고, 출력 옵션은 화면, 보고서, Google Docs 전달을 선택하게 합니다. 프로젝트 단계 게이트는 수업 준비가 된 순서대로 기능을 엽니다. 오류 메시지는 운영자용 코드 대신 교사가 바로 고칠 수 있는 입력과 조치를 알려야 합니다.

기능을 추가할 때에는 클릭 수보다 판단 부담을 줄였는지 확인합니다. 자동 기본값은 수업 의도를 바꾸지 않는 범위에서만 사용합니다.

## 9 특화된 수업 경험과 공통 안전장치를 함께 유지한다

과학 발표, 글쓰기, 프로젝트 전시에는 서로 다른 화면과 질문이 필요합니다. 모든 수업을 하나의 일반 양식으로 만들면 교육적 맥락이 사라집니다. 반대로 프로젝트마다 저장, 인증, AI 호출을 새로 만들면 안전성과 유지보수가 흔들립니다.

목표는 프로젝트별 경험은 독립적으로 설계하고 인증, 저장, 개인정보 최소화, AI 전송, 감사, 삭제는 공통 모듈로 강제하는 것입니다. 프로젝트 1, Meta1, Confesta, Project Expo에 반복된 저장과 Claude 프록시는 이 방향으로 통합할 대상입니다.

제품 결정은 “이 차이가 수업 경험에 필요한가”와 “이 안전장치는 모든 프로젝트에 같아야 하는가”를 분리해서 판단합니다.

## 10 운영 가능성이 곧 신뢰다

좋은 교육 철학도 장애, 데이터 충돌, 만료되지 않는 링크, 삭제되지 않는 기록 앞에서는 신뢰를 잃습니다. 시스템은 실패를 예상하고 제한된 재시도, 충돌 감지, 만료 토큰, 관찰 가능한 품질 게이트를 가져야 합니다.

프로젝트 4 저장소는 Blob 읽기 동시성을 제한하고 일시 오류를 재시도합니다. 방명록은 ETag로 충돌을 감지합니다. 역할 토큰과 관리자 쿠키는 만료됩니다. 앞으로 교사 세션, 자동 파기, 데이터 전송 감사, 핵심 사용자 흐름 테스트를 같은 수준의 운영 기능으로 추가해야 합니다.

배포 완료는 빌드 성공이 아니라 실제 역할별 흐름, 저장, 외부 API, 삭제가 의도대로 동작함을 확인했을 때 선언합니다.

## 11 시스템의 비목표

Feedforward는 다음을 목표로 하지 않습니다.

- AI가 교사를 대신해 학생의 최종 성적과 교육적 판단을 확정하는 시스템
- 학생의 행동을 가능한 한 많이 수집하고 장기간 보관하는 학습 감시 시스템
- 맥락과 루브릭 없이 일반적인 칭찬과 조언을 대량 생성하는 도구
- 서로 다른 평가 관점을 하나의 불투명한 종합 점수로 압축하는 대시보드
- 프로젝트별 화면마다 인증과 저장을 임의로 구현하는 기능 모음
- 학생의 AI 제안 거절을 실패나 비협조로 간주하는 운영 방식
- 개인정보 처리방침과 실제 코드의 차이를 문구로만 덮는 운영 방식

## 12 원칙과 현재 구현 사이의 긴장

| 원칙 | 현재 구현 | 필요한 변화 |
| --- | --- | --- |
| AI에 직접 식별정보를 보내지 않는다 | 일반 평가 프롬프트에 이름, 학년, 반, 모둠 포함 | 전송 전 제거 또는 가명화와 회귀 테스트 |
| 교사만 자신의 평가에 접근한다 | 허용된 숫자 교사 ID가 사실상 입장 키 | 강한 인증, 서버 세션, 소유권 검사 |
| 보유기간이 끝나면 삭제한다 | 공통 자동 파기 작업을 확인할 수 없음 | 데이터별 만료 시각, 예약 삭제, 삭제 확인 |
| 공통 안전장치를 재사용한다 | 프로젝트별 저장과 Claude 프록시 반복 | 공통 저장, 인증, AI, 검증 어댑터 |
| 변경은 검증 가능해야 한다 | 타입 검사는 가능하지만 자동 테스트 명령 부재 | 토큰, 정규화, 저장, E2E 테스트 추가 |
| 정책은 실제 네트워크 경로를 설명한다 | 정책은 AI Gateway, 코드는 제공자 직접 호출 | 호출 경로와 정책을 하나로 맞춤 |

긴장을 공개하는 것은 시스템을 약하게 보이게 하는 일이 아닙니다. 원칙을 실제 우선순위로 바꾸는 출발점입니다.

## 13 제품 결정 질문

새 기능과 변경을 검토할 때 다음 질문에 답합니다.

1. 이 기능은 어떤 학생의 다음 행동을 더 분명하게 만드는가.
2. 교사가 제공하는 기준과 맥락은 무엇인가.
3. AI가 맡는 일과 사람이 최종 책임지는 일은 어디에서 갈리는가.
4. 학생은 결과를 판단하고 수정하거나 이의를 제기할 수 있는가.
5. 어떤 개인정보가 입력되고 저장되고 외부로 전송되며 언제 삭제되는가.
6. 역할별로 꼭 필요한 정보만 보이는가.
7. 실패, 중복 요청, 저장 충돌, 만료를 어떻게 처리하는가.
8. 프로젝트별 차이와 공통 안전장치를 올바르게 분리했는가.
9. 시스템이 만든 결과의 기준과 근거를 설명할 수 있는가.
10. 코드, 정책, 구조 문서, 테스트가 같은 변경에서 함께 갱신되는가.

이 질문에 답할 수 없는 기능은 구현을 시작하기 전에 범위를 다시 정합니다.
